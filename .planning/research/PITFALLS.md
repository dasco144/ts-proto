# Pitfalls Research: ts-proto sharedHelpersFile

**Research Type:** Pitfalls dimension — what can go wrong
**Date:** 2026-02-27
**Confidence:** HIGH (verified by direct source inspection)

---

## Pitfall 1: ConditionalOutput Semantics — All or Nothing in Shared File

**Description:** Helpers like `DeepPartial`, `isSet`, `MessageFns` are built via ts-poet's `conditionalOutput()` which emits the block only if referenced (`v.ifUsed`). For the shared file, the generator must decide whether to emit all possible helpers unconditionally, or scan across all files first.

**Warning signs:** Shared file generates fine but some helpers missing because they weren't "used" in the context they were evaluated in.

**Prevention:** Generate proto-shared.ts by calling `makeUtils(options)` directly, and include all helpers whose option gates are satisfied — not gated by per-file reference counting. The shared file is always comprehensive for the given options.

**Phase:** Implementation

## Pitfall 2: Helper Bodies Are Option-Dependent, Not Static

**Description:** `Builtin`, `DeepPartial`, `toTimestamp`, `MessageFns` all have different bodies based on `forceLong`, `useDate`, `oneof`, `outputEncodeMethods`, etc. You cannot hardcode proto-shared.ts content.

**Warning signs:** proto-shared.ts generates with wrong TypeScript types (e.g., uses `bigint` instead of `Long`).

**Prevention:** Always generate the shared file by calling the existing `makeUtils(options)` infrastructure — never hardcode the helper text. Options are project-level constants, so one shared file per run is correct.

**Phase:** Implementation

---

## Pitfall 3: Import Path Must Be Computed Per File

**Description:** Proto files in nested directories (e.g., `google/protobuf/timestamp.ts`) need `../../proto-shared`, not `./proto-shared`. Each generated file needs a different relative path.

**Warning signs:** TypeScript compiler errors about missing module `./proto-shared` in nested output files.

**Prevention:** Use ts-poet's `imp("SomeName@./proto-shared")` — ts-poet automatically calls `path.relative(dirname(outputPath), importPath)` at `code.toString({ path: moduleName })` time. Do NOT compute paths manually.

**Phase:** Implementation

---

## Pitfall 4: Windows Path Separator Normalization

**Description:** On Windows, `path.relative()` may return backslashes (`..\\proto-shared`) in import paths, which TypeScript does not accept.

**Warning signs:** Tests pass on Linux/Mac CI but fail on Windows.

**Prevention:** If manually constructing any import path strings, normalize with `.replace(/\\/g, "/")`. Verify whether ts-poet's `imp()` handles this internally before adding manual normalization.

**Phase:** Implementation

## Pitfall 5: Integration Test Workflow — Not Jest Snapshots

**Description:** ts-proto integration test expected output files are committed source artifacts (e.g., `integration/simple/simple.ts`), NOT Jest `--updateSnapshot` snapshots. They are regenerated by running `integration/update-code.sh` (or `yarn proto2ts`).

**Warning signs:** Running `jest --updateSnapshot` has no effect on failing integration tests.

**Prevention:**
1. Create new integration test directory (e.g., `integration/shared-helpers/`)
2. Add a `.proto` file and the expected `proto-shared.ts` + generated `.ts` files
3. Regenerate via `yarn proto2ts` to get actual output, then commit as expected
4. The Jest test just diffs actual generated output against committed files

**Phase:** Testing

## Pitfall 6: exportCommonSymbols Conflict

**Description:** `exportCommonSymbols=false` (which is forced when `outputIndex=true`, line 310 of `src/options.ts`) causes helpers to be declared without `export`. In proto-shared.ts, all helpers MUST be exported — other files import them.

**Warning signs:** proto-shared.ts generates helper types without `export` keyword, causing import errors in generated files.

**Prevention:** When generating proto-shared.ts, always emit helpers as `export type` / `export function` / `export interface` regardless of `exportCommonSymbols` option value.

**Phase:** Implementation

## Pitfall 7: Helpers That Cannot Move (Proto-type References)

**Description:** Some "helpers" reference user-generated types (`StructWrapperFns` → `Struct`, MongoDB ObjectId helpers → `ObjectId`). These cannot go in proto-shared.ts because proto-shared.ts has no knowledge of user message types.

**Warning signs:** Type errors about unknown types (`Struct`, `ObjectId`) in proto-shared.ts.

**Prevention:** Keep these in the individual generated files as-is even when `sharedHelpersFile=true`. Only the generic helpers (no user type references) belong in proto-shared.ts. (See FEATURES.md for complete list.)

**Phase:** Implementation

## Pitfall 8: globalThisPolyfill Must Be First

**Description:** When `globalThisPolyfill=true`, the `gt` IIFE polyfill must be declared before any other helper that references `globalThis` (they use `gt` instead). Order matters in the shared file.

**Warning signs:** `gt is not defined` runtime errors in generated code when `globalThisPolyfill=true`.

**Prevention:** In `generateSharedHelpers()`, emit the `gt` polyfill first, before all other helpers.

**Phase:** Implementation

---

## Pitfall 9: onlyTypes Interaction

**Description:** When `onlyTypes=true`, no encode/decode/JSON methods are generated — `isSet`, `bytesFromBase64`, `base64FromBytes`, and `MessageFns` members for those methods should not appear. The shared file must respect this.

**Warning signs:** proto-shared.ts contains `isSet` or base64 helpers even when `onlyTypes=true`.

**Prevention:** Apply the same option gates to shared file generation as to per-file generation. Use `makeUtils(options)` to get the option-correct versions.

**Phase:** Implementation
